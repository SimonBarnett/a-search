# FR-226: Auth provider registry pluggable contact claims

**Repo:** SimonBarnett/a-search
**Phase:** 5 - ComponentsPiece
**Shape:** service (unchanged; login is delivery)
**Issue:** #1236

## Goal
Implement provider registry so adding an OAuth provider is config + adapter;
each provider must expose email OR phone OR contact.

## Decision (LOCKED)

- Config: `shared/auth/registry.json` lists providers with `id`, `label`,
  `enabled` (boolean), `kind`. Shortlist scaffolds (x, github, facebook,
  google, instagram) ship **enabled: false** (stay-dark until credentials).
- Pluggable adapters: `registerAuthAdapter(id, { exchange })` / `getAuthAdapter`
  in `shared/auth/registry.js` -- add a fixture or real provider **without**
  editing the core module (tests prove this).
- Adapter `exchange` returns normalized claims:
  `{ email?, phone?, contact?, provider, subject }`.
- `normalizeAuthClaims` / `acceptAuthResult` **fail closed**
  (`AuthContactError` / `contact_required`) when none of email|phone|contact
  are present (FR-225 rule).
- Out of scope: UI buttons for every network; Stripe; live OAuth token exchange.

## Deliverables
- registry.json + registry module
- Adapter interface + registerAuthAdapter
- enabled flag per provider
- Decision LOCKED + pins

## Testable
- tests/components-piece-auth-registry.test.js add fixture provider without core edit
- Reject adapter result with no contact fields

## Out of scope
- UI buttons for every possible network
- Stripe
